# Allur Digital Twin — архитектура, данные, технологии

Цифровой двойник автомобильного завода (кейс «Qostanai Industry Hackathon»): 3D-визуализация линии, мониторинг KPI, инциденты, прогноз простоев, ИИ-агент, наряды и отчёты.

## 1. Архитектура

```
 Источники данных                 Сервер (Python, FastAPI)                      Клиент (браузер)
┌───────────────────┐        ┌───────────────────────────────────┐        ┌──────────────────────────┐
│ Симулятор станков │──────▶ │ sim.py      модель 7 станков, 1,5 с │        │ 3D-линия (three.js)       │
│ (OPC UA / MQTT —  │        │ db.py       SQLite (data/allur.db)  │ WebSocket │ Дашборд, KPI, графики   │
│  место подключения)│       │ case_data   цели, брак, простои, план│◀──────▶│ Ремонт, Прогноз, Данные   │
│ Файл завода .docx │──────▶ │ importer    чтение docx → kv        │ REST   │ Панель мастера, Исполнитель│
│ (data/import)     │        │ orders      наряды, таймеры          │ /api/* │ Аналитика, ИИ-чат, Настр. │
└───────────────────┘        │ agent/ai    ИИ-агент + инструменты  │        └──────────────────────────┘
                             │ offline     ответы без ИИ-ключа     │
        Внешние сервисы      │ reports     PDF / Excel / Word      │
┌───────────────────┐        │ bot         Telegram-бот (выкл.)    │
│ Gemini / Claude / │◀──────▶│ main        API, WebSocket, статика │
│ Ollama (ИИ)       │        └───────────────────────────────────┘
│ Telegram Bot API  │
└───────────────────┘
```

Поток данных: симулятор каждые 1,5 с вычисляет состояние станков → сервер рассылает его по WebSocket и каждые 30 с пишет снимок в SQLite → браузер рисует 3D-сцену, KPI и графики. Команды (скорость, остановка, наряды, правила автоматики) идут обратно через REST и сразу меняют поведение симулятора.

Основные модули (`server/`): `main.py` (API и сайт), `sim.py` (симулятор, автоматика, прогноз), `orders.py` (наряды), `case_data.py` и `importer.py` (данные кейса), `agent.py`, `ai.py`, `offline.py` (ИИ), `reports.py` (отчёты), `bot.py` (Telegram), `db.py`, `shifts.py`, `seed.py`, `secure.py`, `config.py`.
Клиент (`web/`): `index.html`, `line.js` (3D), `panel.js` (мониторинг, прогноз, ремонт), `master.js` (наряды), `analytics.js`, `aiset.js`, `extra.js`, `themes.js` и `themes.css` (темы).

## 2. Используемые данные

| Данные | Откуда | Где хранятся |
|---|---|---|
| Работа линий (план/факт/загрузка), простои оборудования, план по моделям, показатели качества, схема участков, цели (OEE ≥ 85 %, брак ≤ 2 %, простой ≤ 60 мин/сутки, выпуск ≥ 5 500 авто/мес, 2 смены по 8 ч) | Файл кейса `Plant_data_Allur.docx` (01–02.10.2026), можно загрузить свой в «Аналитике» | таблица `kv` |
| Оперативные показатели станков (температура, вибрация, загрузка, статус, выпуск) | Симулятор `sim.py` (замена на OPC UA / MQTT не меняет остальной код) | таблица `snapshots` |
| События и аварии | Симулятор, правила автоматики, ИИ-агент | таблица `incidents` |
| Наряды: из документа, автоматические по авариям, ручные | `orders.py` | таблица `orders` |
| Демо-история за ~2 суток | `seed.py` | `snapshots` / `incidents` |
| Получатели отчётов Telegram, правила автоматики | пользователь | `subscribers`, `kv` |

Расчёты по данным: OEE = доступность × производительность × качество; прогноз простоя по тренду температуры («авария через N мин»); узкое место линии; прогноз выпуска за месяц; оценка эффекта (сокращение простоев на 30 %, возврат брака к норме).

## 3. Технологии

- **Сервер:** Python 3.10–3.12, FastAPI, Uvicorn (REST + WebSocket), SQLite, httpx, python-dotenv.
- **Отчёты:** ReportLab (PDF), openpyxl (Excel), python-docx (Word, а также чтение входного файла).
- **Клиент:** HTML / CSS / JavaScript без сборки, three.js r128 (3D), Chart.js 4.4 (графики), Lucide (иконки), шрифт Inter. 19 палитр × светлая/тёмная тема.
- **ИИ:** агент с инструментами (чтение состояния, скорость, остановка, правила, наряды, симуляция аварий); вопросы отвечаются одним запросом, команды — через вызов инструментов. Без ключа работает офлайн-режим.
- **Запуск:** `start.bat` / `start.sh` создают виртуальное окружение и ставят зависимости.

## 4. Внешние компоненты

| Компонент | Назначение | Обязателен |
|---|---|---|
| CDN: jsDelivr, cdnjs, Google Fonts | three.js, Chart.js, Lucide, шрифт (нужен интернет в браузере) | да |
| Google Gemini API | ИИ-агент (основной вариант, модели flash-lite / flash) | нет, без него офлайн-режим |
| Anthropic Claude API | ИИ-агент (альтернатива) | нет |
| Ollama (локально) | ИИ без ключа и интернета | нет |
| Telegram Bot API (aiogram, long polling) | рассылка отчётов и оповещений, управление админом | нет, по умолчанию выключен |
| OPC UA / MQTT | подключение реального оборудования (место зарезервировано в `layout.json` и `sim.py`) | нет, сейчас симулятор |

## 5. Безопасность и ограничения

- Ключи ИИ и токены хранятся в `.env` / `API_KEY.txt`, в интерфейс отдаются только последние 4 символа, из логов и ошибок они вырезаются (`secure.py`); менять ключ можно только с компьютера, где запущен сервер.
- Авторизации на сайте нет (демо): перед публикацией наружу её нужно добавить.
- Данные станков — результат симуляции, а не реальные измерения; для реального завода подключается OPC UA / MQTT.

## 6. Предполагаемый эффект

**Что даёт решение:** прозрачность состояния всех участков в одном окне, раннее предупреждение о простоях, сокращение времени реакции на аварию (наряд создаётся автоматически), контроль отклонений от целей, отчёт за смену без ручной сборки.

**Количественная оценка** (приложение считает её само по данным кейса за 01–02.10.2026, раздел «Аналитика → Оценка потенциального эффекта»):

| Показатель | Значение | Как получено |
|---|---|---|
| Внеплановые простои по данным | ≈ 60 мин/сутки | (25 + 40 + 55 мин) ÷ 2 дня; плановое ТО не считается |
| Эффект от сокращения простоев на 30 % | **+104 авто/мес** | 60 мин × 30 % × 0,25 авто/мин (план 120 авто за смену) × 23 рабочих дня |
| Эффект от возврата брака окраски и сварки к норме 2 % | **+133 годных авто/мес** | превышение нормы × выпуск участка × 2 смены × 23 дня |
| Прогноз годного выпуска за месяц без изменений | 5 451 авто (99 % цели) | годные за смену × 2 смены × 23 дня |
| Разрыв до цели 5 500 авто/мес | 49 авто | 5 500 − 5 451; оба эффекта его перекрывают |

**Отклонения, которые решение уже выявляет по данным кейса:** брак окраски 4,3 % и сварки 2,2 % (норма ≤ 2 %); Конвейер-03 — простой 55 мин, 92 % от лимита 60 мин; план по моделям 4 800 авто при цели 5 500 (расхождение 700).

**Как читать цифры.** Это ориентировочная оценка на двух днях тестовых данных. Допущения: сокращение простоев на 30 % (взято как целевое, не измерено), темп последней линии 15 авто/ч, 23 рабочих дня в месяц. Экономический эффект в деньгах не считался: в кейсе нет стоимости автомобиля и простоя. Реальную цифру даёт пилот на данных не менее чем за месяц.

## 7. Ограничения

- **Данные станков симулируются.** Температура, вибрация и загрузка не измеряются на реальном оборудовании, поэтому прогноз простоев показывает принцип работы, а не реальную точность.
- **Малая выборка.** Данные кейса охватывают 2 дня и 3 участка; статистических выводов и точности прогноза на них сделать нельзя.
- **Прогноз простоев** строится по линейному тренду температуры за последние ~16 замеров (время до критической температуры), без обучения на истории аварий. Вибрация и другие признаки в расчёт времени до аварии отдельно не входят. Уровень риска зависит ещё от текущего статуса станка.
- **Учтены не все участки кейса:** брак и простои привязаны к трём участкам (сварка, окраска, сборка); склады и контроль качества в данных кейса не заданы.
- **ИИ-ассистент** зависит от внешнего сервиса и ключа. При перегрузке или без ключа отвечает офлайн-режим по ключевым словам, он проще и может ответить менее точно. Ответы ИИ нужно проверять, прежде чем принимать решения.
- **Безопасность:** на сайте нет авторизации и ролей (роли в демо условные), нет шифрования канала (HTTP). В текущем виде решение рассчитано на демонстрацию и закрытую сеть.
- **Одна линия, один экземпляр сервера:** хранение в SQLite, без резервирования и масштабирования на несколько цехов.
- **Для 3D, графиков и шрифтов нужен интернет** (библиотеки подключаются с CDN); офлайн-вариант потребует их локальной копии.
- **Мобильной раскладки нет:** интерфейс рассчитан на экран компьютера.

## 8. Условия внедрения

**Технические**
1. Сервер или ПК в сети завода с Python 3.10–3.12; в `.env` указать `HOST=0.0.0.0`. Требования к ресурсам для одной линии не измерялись (приложение лёгкое, но точные цифры нужно снять на пилоте).
2. Подключение источников данных: шлюз OPC UA или MQTT к контроллерам станков (формат тегов описан в `server/layout.json`), замена симулятора в `server/sim.py` без изменения остального кода.
3. Интеграция с ERP/MES для плана выпуска и нарядов (сейчас план и задачи берутся из загружаемого docx).
4. Перед открытием наружу: авторизация и роли, HTTPS, резервное копирование `data/allur.db`.
5. Локальная копия библиотек (three.js, Chart.js), если на заводе нет доступа к CDN; ключ ИИ или локальная модель Ollama, если внешний ИИ недопустим по политике безопасности.

**Организационные**
1. Назначить владельца данных и ответственных: мастер (наряды), диспетчер (мониторинг), руководитель (аналитика).
2. Согласовать с заводом пороги и цели (OEE, допустимый брак, лимит простоя, смены); они задаются в файле данных и `.env` и меняются без правки кода.
3. Обучение персонала: 30–60 минут на роль (диспетчер, мастер, исполнитель).

**Этапы**
1. **Пилот (1–2 месяца):** одна линия, реальные данные с 3–7 станков, сравнение прогноза с фактическими простоями.
2. **Калибровка:** настройка порогов и правил, оценка точности прогноза и фактического сокращения простоев (проверка допущения 30 %).
3. **Масштабирование:** остальные линии и цеха, интеграция с ERP/MES, перенос хранилища на промышленную СУБД при росте объёма.

**Критерии успеха пилота:** сокращение внеплановых простоев, доля аварий, предсказанных заранее, рост OEE к цели 85 %, снижение брака до 2 %, сокращение времени от аварии до наряда.
